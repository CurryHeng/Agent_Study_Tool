# 一、系统总体设计目标

## 1.1 设计目标

StudyForge 的总体设计目标是构建一个以 **AI Agent 为核心的智能学习系统**，面向大学生期末复习场景，将用户已有的课程资料转化为结构化知识和可练习的题库。

系统总体流程为：

```text
课程资料
   ↓
资料解析
   ↓
知识结构化
   ↓
思维导图
   ↓
AI题库
   ↓
AI审核
   ↓
刷题
   ↓
错题
```

在此基础上增加统一的：

```text
              用户
                ↓
        Navigator Agent
                ↓
          理解用户需求
                ↓
          调度专业 Agent
```

使用户不需要理解系统内部各个 Agent 的工作方式，而是可以通过自然语言或界面操作完成学习任务。

### 这里有一个非常重要的设计原则

我们把：

> **Agent 和普通业务代码分开。**

例如：

|功能|推荐实现|
|---|---|
|用户登录|普通业务代码|
|文件上传|普通业务代码|
|PDF读取|普通程序|
|文件存储|普通程序|
|数据库存取|普通程序|
|权限控制|普通程序|
|文档内容理解|Agent|
|知识点提取|Agent|
|思维导图结构生成|Agent|
|题目生成|Agent|
|题目质量判断|Agent|
|任务规划|Navigator Agent|
|Agent调度|Orchestrator|

也就是说：

> **不要为了“Agent 化”而把所有功能都做成 Agent。**

这是你们后面开发时非常重要的一条原则。

# 三、系统功能模块设计

## 3.1 系统功能模块总体划分

根据需求分析，StudyForge 系统划分为以下六个主要功能模块：

```text
                         StudyForge
                             │
       ┌───────────┬─────────┼─────────┬───────────┐
       ↓           ↓         ↓         ↓           ↓
   用户与课程    资料管理   知识整理   AI题库     学习训练
                                                     │
                                                     ↓
                                               错题与统计
                             │
                             ↓
                       AI智能助手
```

具体模块如下：

|一级模块|主要功能|
|---|---|
|用户与课程管理|用户、课程、学习空间管理|
|学习资料管理|上传、解析、查看、删除课程资料|
|AI知识整理|知识点提取、知识结构、思维导图|
|AI题库|自动出题、AI审题、题库管理|
|学习训练|刷题、判题、答案解析、错题|
|AI智能助手|功能指导、意图理解、任务规划与调度|

---

# 3.2 用户与课程管理

该模块负责建立用户与课程之间的关系，为后续资料、知识点、题库和学习记录提供统一的组织空间。

### 主要功能

```text
用户与课程管理
│
├── 用户信息
├── 课程创建
├── 课程查看
├── 课程删除
└── 学习空间
```

系统以课程作为主要组织单位。

例如：

```text
高等数学
│
├── 学习资料
├── 知识点
├── 思维导图
├── 题库
├── 错题
└── 学习记录
```

这样可以避免不同课程的资料和题目相互混淆。

---

# 3.3 学习资料管理

资料管理模块负责学习资料从上传到结构化处理的基础流程。

### 功能结构

```text
资料管理
│
├── 文件上传
├── 文件存储
├── 文件解析
├── 解析状态管理
└── 资料查看/删除
```

### 基本流程

```text
用户上传资料
      ↓
文件格式检查
      ↓
保存原始文件
      ↓
文档解析
      ↓
结构化文本
      ↓
交给知识整理模块
```

这里需要明确一个系统边界：

> **文件解析属于普通程序能力，文档内容理解属于 Agent 能力。**

例如 PDF 转文本、Markdown 读取等可以由普通程序完成；章节理解、知识点提取则交给 Knowledge Agent。

---

# 3.4 AI知识整理模块

该模块负责将原始课程资料转化为结构化知识。

### 功能结构

```text
AI知识整理
│
├── 章节识别
├── 知识点提取
├── 知识层级构建
├── 思维导图生成
└── 知识结构查看
```

### 核心流程

```text
结构化课程资料
        ↓
   Knowledge Agent
        ↓
     章节识别
        ↓
     知识点提取
        ↓
     层级关系构建
        ↓
    ┌───┴────┐
    ↓        ↓
知识结构   思维导图
```

### 设计目标

用户不需要手动整理课程知识结构。

例如用户上传：

> 《高等数学期末复习提纲.pdf》

系统自动形成：

```text
高等数学
│
├── 第一章 函数与极限
│   ├── 函数
│   ├── 极限
│   └── 连续性
│
├── 第二章 导数与微分
│   ├── 导数
│   ├── 微分
│   └── 导数应用
│
└── 第三章 积分
    ├── 不定积分
    ├── 定积分
    └── 积分应用
```

并自动生成对应思维导图。

因此：

> **自动知识整理 + 思维导图属于 P0 核心能力。**

# 3.6 学习训练模块

学习训练模块主要采用传统业务逻辑实现，不需要所有功能都交给 Agent。

```text
学习训练
│
├── 选择题库
├── 开始刷题
├── 提交答案
├── 自动判题
├── 查看解析
├── 错题记录
```

```text

   ↓

   ↓

```

> **错因分析、薄弱知识点分析**

# 3.7 AI智能助手模块

```text
AI智能助手

├── 用户意图理解

├── 任务执行

```

> “帮我根据这份资料出20道选择题。”

用户无需知道：

- Document Agent 是什么
    
- Question Agent 是什么

这是整个项目总体设计的**核心部分**。

---

# 4.2 Navigator Agent

### 定位

Navigator Agent 是系统的**统一智能入口**。

### 主要职责

1. 理解用户自然语言需求
    
2. 判断用户意图
    
3. 提供系统功能指导
    
4. 将用户需求转化为任务
    
5. 将任务交给 Orchestrator
    
6. 汇总执行结果并反馈给用户
    

### 不负责

Navigator Agent 不直接负责：

- PDF解析
    
- 知识点提取
    
- 题目生成
    
- 题目审核
    
- 数据库操作
    

它只负责：

> **“理解用户要做什么。”**

---

# 4.3 Agent Orchestrator

### 定位

Orchestrator 是 Agent 系统的**任务执行和调度中心**。

采用：

> **LangGraph**

进行实现。

### 主要职责

```text
任务接收
   ↓
任务拆解
   ↓
确定执行顺序
   ↓
调用专业Agent
   ↓
判断执行结果
   ↓
条件分支
   ↓
失败重试/任务调整
   ↓
结果汇总
```

因此两者的职责可以简单概括为：

|模块|核心问题|
|---|---|
|Navigator Agent|**用户想做什么？**|
|Orchestrator|**应该怎么完成？**|
|专业 Agent|**具体把事情做好。**|

---

# 4.4 Document Agent

### 主要职责

负责对已经完成基础解析的文档进行内容理解。

```text
结构化文本
    ↓
Document Agent
    ↓
章节识别
    ↓
内容理解
    ↓
结构化课程内容
```

### 不负责

- 原始文件上传
    
- 文件保存
    
- 数据库存储
    

这些由普通后端完成。

---

# 4.5 Knowledge Agent

### 主要职责

负责从课程内容中建立知识结构。

```text
课程内容
   ↓
Knowledge Agent
   ↓
知识点提取
   ↓
知识关系
   ↓
知识层级
   ↓
思维导图数据
```

---

# 4.6 Question Agent

负责根据知识点生成题目。

输入：

```text
课程
章节
知识点
题型
数量
难度
```

输出：

```text
题目
├── 题干
├── 选项
├── 答案
├── 解析
├── 知识点
└── 难度
```

具体字段在**详细设计阶段**再确定。

---

# 4.7 Review Agent

Review Agent 负责对 Question Agent 生成的题目进行质量审核。

```text
生成题目
   ↓
Review Agent
   ↓
┌─────────────────┐
│ 正确性检查       │
│ 答案检查         │
│ 知识点匹配       │
│ 题目质量         │
│ 表述合理性       │
└────────┬────────┘
         ↓
     审核结果
      ↙    ↘
    PASS   FAIL
     ↓      ↓
    题库   重新生成
```

# 五、Agent 任务调度设计

这是 Navigator + Orchestrator 架构最关键的地方。

---

## 5.1 简单任务

例如：

> “什么是题库？”

流程：

```text
用户
 ↓
Navigator
 ↓
判断为普通咨询
 ↓
直接回答
```

无需调用专业 Agent。

---

## 5.2 单 Agent 任务

例如：

> “帮我生成10道选择题。”

```text
用户
 ↓
Navigator
 ↓
识别出题需求
 ↓
Orchestrator
 ↓
Question Agent
 ↓
Review Agent
 ↓
返回结果
```

---

## 5.3 多 Agent 任务

例如：

> “把这份高数资料整理成思维导图，然后出20道选择题。”

Orchestrator 形成任务链：

```text
Task
 │
 ├── ① 文档解析
 │
 ├── ② 知识点提取
 │
 ├── ③ 思维导图生成
 │
 ├── ④ 生成20道选择题
 │
 └── ⑤ AI审核
```

执行：

```text
Document Agent
       ↓
Knowledge Agent
       ↓
Question Agent
       ↓
Review Agent
       ↓
Navigator
       ↓
用户
```

# 六、LangGraph 工作流设计

这里开始体现 LangGraph 的价值。

我们暂时不进入代码，只确定工作流。

## 6.1 Agent 状态

整个任务应该拥有一个统一的：

> **Task State**

可以理解为：

```text
Task State
│
├── 用户请求
├── 当前任务
├── 当前状态
├── 课程信息
├── 文档信息
├── 知识结构
├── 题目结果
├── 审核结果
└── 错误信息
```

这样不同 Agent 可以围绕同一个任务状态协作。

---

# 6.2 LangGraph 核心流程

```text
                START
                  │
                  ▼
           Navigator Agent
                  │
                  ▼
            Task Planning
                  │
                  ▼
             Task Router
                  │
       ┌──────────┼──────────┐
       ↓          ↓          ↓
   Document    Knowledge   Question
      │           │          │
      └───────────┼──────────┘
                  ↓
             Review Agent
                  │
             ┌────┴────┐
             ↓         ↓
           PASS       FAIL
             │         │
             ↓         └────→ Question Agent
          Task End
             │
             ▼
           用户
```

这里的关键是：

> **FAIL 可以形成循环。**

这正是 LangGraph 比简单的线性 Agent Chain 更适合你们项目的原因之一。

# 八、RAG 总体设计

你们已经确定使用 RAG，所以总体设计中需要把它纳入架构。

---

## 8.1 RAG 的作用

RAG 主要用于让 Agent 能够基于**用户自己的课程资料**进行回答和生成。

例如：

> “根据我上传的高数资料，解释一下拉格朗日中值定理。”

系统不是完全依赖模型自身知识，而是：

```text
用户问题
   ↓
Navigator
   ↓
检索课程知识
   ↓
Vector DB
   ↓
相关资料
   ↓
LLM
   ↓
回答
```

---

# 8.2 文档入库流程

```text
课程资料
   ↓
文本解析
   ↓
文本切分
   ↓
Embedding
   ↓
Vector DB
   ↓
建立课程知识索引
```

同时：

```text
结构化业务数据
       ↓
     SQLite
```

因此：

> **SQLite 负责结构化业务数据，Vector DB 负责语义检索数据。**

# 十一、系统安全与可靠性设计

总体设计阶段简单写即可。

## 11.1 数据安全

- 用户课程资料进行独立管理
    
- 不同用户的数据相互隔离
    
- 原始文件与结构化数据分别存储
    

## 11.2 Agent 安全

- 限制 Agent 可调用的工具
    
- 限制 Agent 可访问的数据范围
    
- 对 Agent 输出进行格式校验
    
- 对关键操作进行后端验证
    

## 11.3 AI 输出可靠性

采用：

> **生成 → 审核 → 入库**

而不是：

> **生成 → 直接入库**

对于题目尤其如此。

# 十二、系统扩展性设计

你们现在只实现：

```text
Navigator
   ↓
Orchestrator
   ↓
Document
Knowledge
Question
Review
```

以后可以很自然地扩展：

```text
                 Orchestrator
                      │
       ┌──────────────┼──────────────┐
       ↓              ↓              ↓
   Error Agent    Tutor Agent    Plan Agent
       │              │              │
     错因分析        AI答疑         学习计划
```

这也是为什么现在要把 **Navigator 和 Orchestrator 分开**。

如果以后增加十几个 Agent，Navigator 不需要重新实现所有调度逻辑，只需要让 Orchestrator 增加新的 Agent 节点和工作流。
