# EStudy 后端反向解构报告

> 基于 `backend/` 真实代码，仅作分析，不修改任何代码。
> 目的：回答「这个后端现在到底是怎么工作的」。

---

## 1. 整体架构与目录职责

后端是 **FastAPI 单体**，严格分层：`api → services → repositories → models`，另有三个横向支撑：`rag/`（向量检索）、`parsers/`（文档解析）、`workflow/`（LangGraph 编排）。

```
backend/
├── main.py            # 应用入口：CORS + 注册 9 个路由 + AccessError 全局异常处理 + /api/health
├── config.py          # pydantic-settings 读 .env（DB/LLM/上传/JWT 全部配置）
├── db/                # base.py(Base+时间戳Mixin+utcnow) / engine.py(引擎+SQLite外键pragma+SessionLocal) / session.py(get_db)
├── models/            # 12 个 SQLAlchemy 模型 + enums.py（唯一 schema 真相源）
├── schemas/           # Pydantic 请求/响应模型（11 个）
├── repositories/      # 数据访问层（10 个，薄封装，仅 SQL/ORM 操作）
├── services/          # 业务层（19 个，含确定性算法与编排）
├── api/               # 路由层（9 个 router + deps.py）
├── workflow/          # LangGraph：state.py(TaskState) + graph.py(图)
├── rag/               # chunker / embedding / chroma / retriever
├── parsers/           # base / factory / pdf / markdown / word / ppt / image / text_utils
├── seed/              # 种子脚本（系统账号/工作簿 + 154 内置题）
├── alembic/           # 迁移（env.py + 1 个 init_schema 版本）
└── tests/             # 15 个测试文件 + conftest.py
```

**关键分层契约**：`api` 只做参数校验 + 调 service + `db.commit()`；`service` 做业务逻辑（只 `flush` 不 commit）；`repository` 只做单表/单查询的 ORM；`models` 定义表结构。**Agent 层（workflow）不直接碰 repository，复用 service。**

## 2. API → Service → Repository → Model 实际调用关系

真实调用链（单向，下层不依赖上层）：

```
API(router) → Service → Repository → Model(SQLAlchemy) → SQLite
                    ↘ rag/parsers/workflow  # 横向能力
```

示例（题目更新）：

```
api/questions.py:update_question → question_service.update_question
  → access.get_owned_question（权限）→ question_repository.get_by_id
  → question_option_repository.replace → QuestionOption
```

**特殊路径**：

- `api/deps.py:get_current_user`（依赖注入）→ `security.decode_access_token` + `user_repository.get_by_id`，供所有需鉴权的路由复用。
- `main.py` 的 `AccessError` 异常处理器，把 service 抛出的 `AccessError(status, msg)` 统一转成 `{"detail": msg}`。

## 4. 核心业务流程（简化调用链）

### ① 登录

```
POST /auth/login → auth_service.login
  → user_repository.get_by_email → security.verify_password
  → _issue_tokens: create_access_token(15min) + generate_refresh_token(64字节hex)
  → refresh_token_repository.create（只存 sha256 哈希）
```

### ② 文档解析

```
POST /documents/upload(multipart) → document_service.upload_document
  → access.get_owned_workbook → factory.detect_type(扩展名)
  → document_repository.create(status=pending) → 存文件 data/uploads/{id}.{ext}
  → factory.parse_file → ParsedDocument（各 parser 产出 Section 列表）
  → _save_parsed（JSON 落盘 uploads/parsed/{id}.json）
  → knowledge_service.import_sections（章节/知识点写 Knowledge 树）
  → status=success
```

### ③ RAG

```
入库: POST /documents/{id}/index → rag_service.index_document
  → document_service.read_parsed_sections → knowledge_repository.list_by_document
  → chunker.chunk_document(章节→chunk, 带 knowledge_id) → embedding(ONNX)
  → VectorStore.upsert（Chroma, metadata=workbook_id/document_id/section/knowledge_id）

检索: POST /rag/retrieve → rag_service.retrieve
  → embed_query → VectorStore.query(where: workbook_id [+knowledge_id]) → top-k
```

### ④ AI 出题/审题

```
POST /questions/generate → generation_service.generate_questions
  → rag_service.build_context（RAG 片段 + 知识点名）
  → 循环 3 次: ① llm.generate_json(生成 prompt)→GenerationOutput
              ② model_validate(结构校验) ③ validate_question(业务校验)
              ④ llm.generate_json(审核 prompt)→ReviewResult(语义审核)
  → _save_questions(source=ai, status=approved, 选项写 question_options)
```

### ⑤ 刷题/判题

```
POST /questions/{id}/answer → review_service.answer_question
  → grading.grade_question(结构化判题, 无正则)
  → _derive_rating(strict 强制派生 good/again)
  → answer_record_repository.create(AnswerRecord)
  → 错则 wrong_record_repository.record(生成/更新 WrongRecord)
  → review_card_repository.get_or_create + sm2.review_card + apply_sm2(SM-2)
```

### ⑥ 错题 / SM-2

- **AnswerRecord**：每次作答都写（只增）。
- **WrongRecord**：答错才写，同题只留最新一条。
- **ReviewCard**：SM-2 调度（ease/interval/repetitions/next_review/total_*）。
- `GET /wrong-records` 联查 question 显示题干+正确答案。

### ⑦ Agent

```
POST /agent/chat → agent_service.run_task
  → build_graph(db,user)(工厂闭包) → graph.invoke(TaskState)
    navigator(LLM 分类意图) → 条件路由 → question/mindmap/document/direct_answer 节点
    → question 空则回环重试(≤2) → result_handler 组装 → END
```

## 5. workflow 三文件真实执行关系

- **`state.py`**：`TaskState` 只是一个 `TypedDict`（`total=False`，全字段可选），**无任何行为**。它只是给 LangGraph 当 state schema 用的类型标注，字段：`task_id/user_id/user_request/intent/params/current_step/generated_data/retry_count/errors/final_result`。
- **`graph.py`**：`build_graph(db, user, navigator_llm, generate_fn, workbook_hint)` 是一个**工厂函数**，闭包捕获 `db`+`user`（这样节点能直接用请求的 session 调 service），返回 `StateGraph`。节点是闭包函数，`add_node` + `add_edge(START→navigator)` + `add_conditional_edges`（navigator→按 intent 分派；question_agent→按是否空+retry 决定回环）。
- **`agent_service.py:run_task`**：入口。每次调用**新建一个图**（`build_graph`），生成 `task_id`，组装初始 `TaskState`，`graph.invoke(initial)` 同步执行，取 `final_result` 返回。

**执行顺序**：`invoke → navigator(LLM 出 intent/params) → 条件边按 intent 跳到 agent 节点 → agent 节点写 generated_data → (question 空则回环) → result_handler 写 final_result → END`。

**⚠️ 与 docs 的差异**：docs 里「Navigator」和「Orchestrator」是两个概念，但真实代码里 **没有独立的 Orchestrator 节点**——"编排/路由/重试决策"被编码成两个**条件边函数**（`route_after_navigator`、`route_after_question`）。Navigator 才是唯一的 LLM 节点。

## 6. 核心 / 重复 / 测试 / 兼容代码

**真正核心（业务价值所在）**

- `services/sm2.py`（SM-2 算法）、`services/grading.py`（判题）
- `services/generation_service.py`（出题+审核编排）、`services/llm_service.py`
- `services/review_service.py`（刷题主流程）、`services/rag_service.py`
- `services/question_service.py` / `workbook_service.py` / `document_service.py` / `auth_service.py` / `access.py` / `mindmap_service.py` / `wrong_record_service.py`
- `workflow/graph.py` + `agent_service.py`（编排）、`parsers/`、`rag/`

**重复 / 冗余**

- `question_service._visible_workbook_ids` 与 `review_service._visible_workbook_ids` 各自实现了一遍「`[系统0] + 用户练习册`」，逻辑重复（应抽到 `access`）。
- `services/chapter_sort.py` 的 `parse_chapter_number` 是从旧 TS 移植的，旧项目里还留着 TS 版本（不在新后端内，但属历史重复）。

**测试专用 / 兼容**

- `tests/` 全部、`conftest.py`（function 级 engine 每测试建库 + Mock LLM/FakeEmbedder）。
- `seed/seed.py`（种子，运行时用）。
- `parsers/image.py`（占位）、`parsers/pdf.py`（启发式，未真实验证）→ 属于"半成品"。

## 7. 未完成 / 假实现 / 断点 / 架构问题

**未完成 / 假实现**

1. `short_answer` 判题未实现（`grading.grade_question` 直接 `return False`，注释说明需 LLM）。
2. 图片解析：`parsers/image.py:parse` 抛 `NotImplementedError`，上传图片返 501。
3. `direct_answer`（chat 意图）返回**固定字符串**，不是 LLM 回答。
4. Review Agent 不是独立 LangGraph 节点——审核内聚在 `generation_service` 里（图只兜底"空产重试"）。
5. `agent_tasks` 表从未写入（Agent 执行日志未落库）；`api_keys` 表未用（用户密钥加密存储未接入）。
6. 无 LangGraph checkpoint 持久化（纯内存，单请求）。

**功能断点**

7. 前端 `workbookApi.list()` 只返回用户练习册，**系统工作簿(id=0)不暴露** → 内置 154 题前端不可见。
8. `documents` 删除**不清理 Chroma 向量**（`rag` 无 delete 接口）。
9. 无考试/session 表，严格模式 session 靠前端内存。
10. `review_service.get_due` 每次为所有可见题 `get_or_create` 建卡（一次性性能开销）。

**架构问题 / 隐患**

11. **双重重试**：图级 `MAX_RETRIES=2` + `generation_service` 内部 `MAX_ATTEMPTS=3`，语义重叠（极端情况最多 9 次生成调用）。
12. `build_graph` 每次请求新建图（闭包 db+user），无复用。
13. `rag_service` 每次调用新建 `VectorStore` + `embedder`（无单例缓存）。
14. 事务靠约定：service 只 `flush`，route 层 `db.commit()`；无显式事务边界。
15. `config.llm_model` 默认 `deepseek-chat`，与 OpenCode 实际用的 `deepseek-v4-pro` 不一致，真实出题需确认并改 `.env`。

## 结论：这个后端现在到底是怎么工作的？

一个严格分层的 FastAPI 单体，`api` 收请求 → `service` 做业务（确定性逻辑用纯函数，AI 用 `LLMService`+`generation_service`，检索用 `rag_service`）→ `repository` 读 SQLite（向量读 Chroma）；用户意图类请求则进入 `workflow` 的 LangGraph，由 Navigator（LLM 分类）→ 条件路由 → 复用既有 service 的 Agent 节点执行，最后 `result_handler` 汇总返回。

核心业务已闭环（登录→题库→刷题→判题→错题→复习→Agent），但 short_answer 判题、图片解析、Agent 日志、内置题库前端暴露等仍是断点。
