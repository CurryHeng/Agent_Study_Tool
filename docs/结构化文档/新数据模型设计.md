## 1. 旧模型问题总结

### 旧表职责与字段分析（基于 `server/src/db.ts` 与 `db/schema.ts` 真实定义）

| 旧表 | 职责 | 核心问题 |
|---|---|---|
| `users` | 账号 | ✅ 基本健康 |
| `workbooks` | 练习册（复合主键 id+user_id）| ⚠️ 复合主键用 id 存 `'default'`，语义混乱 |
| `questions` | **题目+错题档案 混在一起** | ❌ 最严重：把"题目"和"用户错题记录"焊死在一张表 |
| `cards` | SM-2 复习卡 | ✅ 结构健康，但缺 created_at/updated_at |
| `review_logs` | 复习日志（=答题记录）| ⚠️ 字段名偏"日志"，实为答题记录 |
| `wrong_records` | 错题记录 | ✅ 结构健康，date 语义偏窄 |
| `api_keys` | 用户 API Key（加密）| ✅ 保留 |
| `refresh_tokens` | 认证刷新令牌 | ✅ 保留，但无过期清理 |

### `questions` 表字段逐一裁决（关键分析）

| 旧字段 | 业务含义 | 裁决 | 原因 |
|---|---|---|---|
| `id` | 主键（TEXT，`user-`/`agent-`前缀）| 迁移（改 INTEGER）| 前缀混用是旧体系 hack |
| `user_id` | 出题/拥有者 | **删除** | 违反"题目本身无用户状态"；改为经 workbook 归属 |
| `chapter` | 章节文本 | **拆分** | 文本 → Knowledge 树节点 |
| `question_number` | 错题编号（如 1.1）| 保留（nullable）| 展示用，无业务约束 |
| `original_number` | 原书题号 | 保留（nullable）| 溯源用 |
| `problem` | 题干（含 `(A)(B)(C)(D)`）| **拆分** | 题干→content，选项→question_options |
| `image` | 题目图片 | 保留（nullable）| 题目自身属性 |
| `wrong_answer` | 用户的错误答案 | **迁移** | → WrongRecord（用户专属）|
| `wrong_reason` | 用户的错因 | **迁移** | → WrongRecord（用户专属）|
| `correct_answer` | 正确答案 | 迁移→`answer` | 题目自身属性 |
| `steps` | 核心步骤/解析 | 迁移→`analysis` | 题目自身属性（大量缺失，可空）|
| `summary` | 一句话总结 | 保留→`summary` | 题目自身属性（但需清洗冗余）|
| `knowledge_points` | 知识点标签（JSON 字符串）| **拆分** | JSON 数组 → Knowledge 外键 |
| `workbook_id` | 练习册 | 保留 | 归属 |
| `created_at`/`updated_at` | 时间戳 | 保留 | — |

> **核心洞察（为什么重构）**：旧系统本质是"错题本"，所以 `wrong_answer`/`wrong_reason` 被焊进题目。这正是 docs 与你的要求要打破的——**题目是客观知识，错题是某个用户的主观记录**。

## 2. 新模型设计原则

1. **题目 vs 学习记录彻底分离**：`Question`/`QuestionOption` 不含任何用户状态。
2. **单一真相源**：一张表一个事实，不冗余存储（如选项正确性不双写）。
3. **结构化替代正则**：选项进独立表，绝不从 `problem` 文本正则解析。
4. **外键表达关系**：归属用 FK，不靠 `user_id`/`chapter` 文本 hack。
5. **归一化适度**：不追求 3NF 极致，但保证无矛盾。
6. **类型用枚举约束**：`Question.type` 用 enum，不靠字符串自由填写。

## 3. ER 关系

```text
User 1──────N Workbook          (workbook.user_id)
Workbook 1──N Knowledge         (knowledge.workbook_id)
Knowledge 1──N Knowledge        (自引用 parent_id，构成树)
Workbook 1──N Question          (question.workbook_id)
Knowledge 1──N Question         (question.knowledge_id，可空)
Question 1──N QuestionOption    (option.question_id，CASCADE)

User 1──N ReviewCard            (card.user_id)
Question 1──N ReviewCard        (card.question_id，复合主键)
User 1──N AnswerRecord          (record.user_id)
Question 1──N AnswerRecord      (record.question_id)
User 1──N WrongRecord           (record.user_id)
Question 1──N WrongRecord       (record.question_id)

Workbook 1──N Document          (document.workbook_id)  [P0-4 使用]
User 1──N AgentTask             (task.user_id)          [P0-8 使用]
```

### 关键关系裁决

- **Workbook ↔ Question = 1—N（不是 N—N）**：一道题只属于一个练习册。**为什么**：P0 无跨练习册共享需求；若未来需要"同一题出现在多个练习册"，届时加中间表 `question_workbook(question_id, workbook_id)`，现在不预埋复杂度。
- **Knowledge ↔ Question = 1—N（question.knowledge_id 可空）**：题目可暂未挂知识点。**为什么可空**：迁移/导入时可能还没建好知识树，先落库后补挂。

## 4. 每张表字段定义

### 4.1 users（账号）

| 字段 | 类型 | 非空 | 默认 | 索引 | 说明 |
|---|---|---|---|---|---|
| id | INTEGER PK 自增 | ✅ | — | PK | |
| username | TEXT UNIQUE | ✅ | — | UNIQUE | |
| email | TEXT UNIQUE | ✅ | — | UNIQUE | |
| password_hash | TEXT | ✅ | — | | bcrypt |
| created_at | DATETIME | ✅ | now | | |
| updated_at | DATETIME | ✅ | now | | |

**保留原因**：认证是 P0 必需，字段健康，仅把 TEXT UUID 主键改为 INTEGER 自增。

**系统账号预留**：预留 `id=0` 为系统账号（`username='system'`，`password_hash` 置为不可登录的哨兵值，如 `'!'`）。该账号**不参与任何用户业务**，仅用于承载"系统题库"工作簿（见 4.2 与第 6 节）。**为什么**：内置题需要归属者，但又不属于普通用户；用预留系统账号既保持 `workbook.user_id NOT NULL` 约束完整，又复用现有关系，不引入 `user_id` 可空或 `is_builtin` 标志的额外分支。

### 4.2 workbooks（练习册 = docs 的"课程"）

| 字段 | 类型 | 非空 | 默认 | 外键/索引 | 说明 |
|---|---|---|---|---|---|
| id | INTEGER PK 自增 | ✅ | | PK | |
| user_id | INTEGER | ✅ | | FK→users.id, **CASCADE**, idx | 归属用户 |
| name | TEXT | ✅ | | | 练习册名 |
| description | TEXT | ❌ | | | |
| created_at | DATETIME | ✅ | now | | |
| updated_at | DATETIME | ✅ | now | | |

**改动**：删除旧复合主键 `(id,user_id)`，改为独立自增 PK + `user_id` FK。**为什么**：旧复合主键是为了"同一 `'default'` id 在不同用户下并存"，本质是用主键模拟"每用户一个默认练习册"，语义扭曲。新模型练习册天然有唯一 id，归属靠 FK。

**系统工作簿预留**：预留 `id=0` 为系统工作簿，`user_id=0`（指向系统账号），`name='内置题库'`。所有 `source='builtin'` 的内置题归属此工作簿。**为什么**：内置题库全局共享、只读，不属于任何普通用户；通过系统账号 + 系统工作簿承载，用户的学习记录（ReviewCard/AnswerRecord/WrongRecord）仍按 `question_id + user_id` 正常关联，实现"题共享、记录私有"。

### 4.3 knowledge（知识点树）

| 字段 | 类型 | 非空 | 默认 | 外键/索引 | 说明 |
|---|---|---|---|---|---|
| id | INTEGER PK 自增 | ✅ | | PK | |
| workbook_id | INTEGER | ✅ | | FK→workbooks.id, **CASCADE**, idx | |
| parent_id | INTEGER | ❌ | NULL | FK→knowledge.id, **SET NULL**, idx | 自引用，根节点为 NULL |
| name | TEXT | ✅ | | | 章节/知识点名 |
| description | TEXT | ❌ | | | |
| level | INTEGER | ✅ | 0 | | 树深度（0=章，1=节，2=点）|
| source_document_id | INTEGER | ❌ | NULL | FK→documents.id, SET NULL | 来源文档 |

**为什么自引用 + parent_id**：知识是层级结构（高等数学→函数极限→函数），用 `parent_id` 自关联最自然，也同时服务思维导图与按章节刷题。

### 4.4 questions（题目本身，**零用户状态**）

| 字段 | 类型 | 非空 | 默认 | 外键/索引 | 说明 |
|---|---|---|---|---|---|
| id | INTEGER PK 自增 | ✅ | | PK | |
| workbook_id | INTEGER | ✅ | | FK→workbooks.id, **CASCADE**, idx | 归属练习册 |
| knowledge_id | INTEGER | ❌ | NULL | FK→knowledge.id, **SET NULL**, idx | 挂知识点 |
| type | TEXT(enum) | ✅ | | | single/multiple/true_false/fill_blank/short_answer |
| content | TEXT | ✅ | | | 题干（不含选项）|
| answer | TEXT | ✅ | | | 答案（选择题存 "A"/"ABD"/"T"，填空/简答存文本）|
| analysis | TEXT | ❌ | | | 解析/步骤（旧 steps）|
| summary | TEXT | ❌ | | | 一句话总结 |
| image | TEXT | ❌ | | | 图片路径 |
| difficulty | INTEGER | ❌ | 1 | | 1–5 |
| source | TEXT(enum) | ✅ | 'builtin' | | builtin/imported/ai/user |
| status | TEXT(enum) | ✅ | 'approved' | | generated/reviewing/approved/rejected |
| original_number | TEXT | ❌ | | | 原书题号 |
| question_number | TEXT | ❌ | | | 错题编号（展示）|

**为什么这样设计**：
- `answer` 统一存答案字符串，覆盖所有题型——选择/判断存键，填空/简答存文本。**单一答案字段**，是唯一正确答案事实源。
- 显式移除 `user_id`、`wrong_answer`、`wrong_reason`，切到学习记录表。
- `type`/`source`/`status` 用 **enum 约束**，不用自由字符串。
- `summary` 仅为辅助学习摘要，**不参与判题与核心业务逻辑**。
- 软删除机制：`deleted_at` 标记删除（见第 5 节），所有查询统一过滤 `deleted_at IS NULL`。

### 4.5 question_options（选项，选择题专属）

| 字段 | 类型 | 非空 | 默认 | 外键/索引 | 说明 |
|---|---|---|---|---|---|
| id | INTEGER PK 自增 | ✅ | | PK | |
| question_id | INTEGER | ✅ | | FK→questions.id, **CASCADE**, idx | |
| option_key | TEXT | ✅ | | | A/B/C/D 或 1/2（判断题）|
| content | TEXT | ✅ | | | 选项内容 |
| sort_order | INTEGER | ✅ | 0 | | 展示顺序 |

**最终决策：不加 `is_correct`**（已定稿）。如果选项里存 `is_correct`，而 `questions.answer` 又存 "A"/"ABD"，就出现**两个事实源**，二者可能不一致（这正是 P0-0 发现的"choices/answer 一致性"隐患的来源）。正确答案由 `answer` 唯一决定，判题统一基于 `type + answer`（选择/判断比对选项键，填空/简答比对文本）。`is_correct` 如需展示可随时从 `answer` 推导，不落库。

| 字段 | 类型 | 非空 | 默认 | 外键/索引 | 说明 |
|---|---|---|---|---|---|
| id | INTEGER PK 自增 | ✅ | | PK | |
| user_id | INTEGER | ✅ | | FK→users.id, CASCADE, idx | |
| question_id | INTEGER | ✅ | | FK→questions.id, **RESTRICT**, idx | |
| wrong_answer | TEXT | ❌ | | | 用户的错误答案 |
| wrong_reason | TEXT | ❌ | | | 错因分析 |
| created_at | DATETIME | ✅ | now | | |

### AnswerRecord vs WrongRecord 职责划分

- **AnswerRecord = "发生了什么"**：每次作答的客观事实（答案、对错、时长、模式），**只增不改**，是审计日志，供统计/热力图。
- **WrongRecord = "我的反思"**：错题本条目，含主观 `wrong_reason`，**可编辑**，供错题本 UI 和未来错因分析。
- 关系：一次答错（AnswerRecord.is_correct=false）可以**触发**一条 WrongRecord，但二者独立存在、职责不重叠。

### 4.9 附加表（前瞻，P0-1 建表但 P0-4/8 才用）

- **documents**：id, workbook_id, filename, file_type, file_path, status, created_at（文档解析源）。
- **agent_tasks**：id, user_id, task_type, status, input_data, result_data, error_message, created_at, finished_at（Agent 调试）。
- **api_keys** / **refresh_tokens**：保留旧结构（认证/密钥，非学习数据）。

## 5. 外键与索引策略

| 关系 | 删除行为 | 为什么 |
|---|---|---|
| user → workbook | **CASCADE** | 账号删则其练习册无主，全删 |
| workbook → knowledge | **CASCADE** | 知识树随练习册走 |
| knowledge.parent → 父节点 | **SET NULL** | 删父节点，子树变根，不误删子树 |
| workbook → question | **CASCADE** | 题目归属练习册 |
| question → question_option | **CASCADE** | 选项是题目的组成部分（强组合）|
| question → review_card | **CASCADE** | 卡是题目在学习上的投影（可再生的派生状态）|
| question → answer_record | **RESTRICT** | 不可变历史，禁止静默丢失 |
| question → wrong_record | **RESTRICT** | 用户主观反思，禁止静默丢失 |
| user → review_card / answer_record / wrong_record | **CASCADE** | 账号删则个人学习数据全清 |

**不盲目用 CASCADE 的说明**：
- `knowledge.parent_id` 用 **SET NULL**（不是 CASCADE），因为删一个中间节点不应删掉整棵子树。
- `knowledge_id`、`source_document_id` 用 **SET NULL**（不是 CASCADE），因为删知识点/文档不应删题目，题目降级为"未挂知识点"即可。

**删除策略最终决策（已定稿）：软删除为主，硬删除受 RESTRICT 保护。**
- **软删除**（用户常规"删除题"操作）：设 `questions.deleted_at = now`，不物理删行。历史（AnswerRecord/WrongRecord）完整保留，题目从查询中隐藏（所有查询过滤 `deleted_at IS NULL`），且可恢复（清除 `deleted_at`）。
- **硬删除**（真正的物理删除，仅清理/后台场景）：因 `answer_record`、`wrong_record` 对 question 是 **RESTRICT**，有历史记录的题目无法直接物理删除；只有无任何历史（或已确认删除历史）时才允许，防止不可变审计数据被误删。
- **为什么不用 CASCADE 删历史**：AnswerRecord 是"发生了什么"的不可变事实，WrongRecord 是"为什么错"的反思，都承载长期学习价值，不能随删题静默消失。**为什么不用纯 RESTRICT（无软删除）**：会导致"有历史的题永远删不掉"，用户无法清理；软删除 + RESTRICT 组合兼顾"可清理、可恢复、历史不丢"三者。

**索引清单**：所有 FK 建索引；另建 `(review_cards.user_id, next_review)`（每日到期查询）、`(questions.workbook_id, status)`、`(answer_records.user_id, question_id)`。

## 6. 旧数据迁移策略

### 数据分四类（明确边界）

| 类别 | 内容 | 处理 |
|---|---|---|
| **旧数据迁移** | 154 题 + 练习册名 | 清洗后迁入系统工作簿（id=0），`source='builtin'` |
| **测试数据** | 8 测试账号、乱码题、14 残留 refresh_token | **废弃** |
| **正式种子数据** | 无（未来 AI 出题+审核产出）| 暂空 |
| **AI 生成数据** | 未来 Question Agent 产物 | 走 status=generated→reviewing→approved |

### 154 题具体清洗规则

| 数据 | 问题 | 清洗动作 |
|---|---|---|
| 全部为填空/简答 | 无选择题 | type 统一 `fill_blank`（部分 `short_answer`），**不伪造选项** |
| `problem` | 无 `(A)(B)(C)(D)` | 直接→`content` |
| `correct_answer` | 正常 | →`answer` |
| `steps` | 116/154 缺失 | →`analysis`，缺失留 NULL |
| `summary`==`correct_answer` | 冗余 | 相等则 summary 置 NULL |
| `knowledge_points`(JSON) | 自由标签 | 提取唯一标签 → 建 knowledge 平铺节点并挂 `knowledge_id` |
| `chapter`(文本) | 无序文本 | → knowledge 一级节点（章节层）|
| `wrong_answer`/`wrong_reason` | 题目内嵌"示例错因"| **不迁入 Question**；作为演示数据可生成一条样例 WrongRecord，或直接废弃 |
| 乱码题 | mojibake | 废弃 |
| 测试账号/default 练习册不一致 | 脏数据 | 废弃，重建 |

> **明确结论**：154 题迁入系统工作簿（`source='builtin'`），但**只作为"内置参考数据"**，绝不标为正式可信题库；正式题库由 AI 出题 + Review Agent 审核产出，逐步替换这些参考题。

│   ├── document.py  agent_task.py  api_key.py  refresh_token.py
│   └── __init__.py        # 汇总导入，供 Alembic autogenerate 识别

**为什么这样分**：`models/` 是唯一真相源（不再有 schema.py + 手写 SQL 双份）；`db/` 集中管理连接与 Base；`alembic/` 独立管理版本迁移。

---

## 8. Alembic 迁移方案

- **初始化**：`alembic init alembic`，`env.py` 指向 `backend/models` 的 `Base.metadata` 与 `config.DATABASE_URL`。
- **版本管理**：每次改模型 → `alembic revision --autogenerate` 生成版本 → `alembic upgrade head` 应用。
- **初始化数据库**：`alembic upgrade head` 建全表（替代旧 `CREATE TABLE IF NOT EXISTS`）。
- **种子数据**：`seed/seed.py` 用 Alembic 之外的独立脚本写入内置题库（种子 ≠ 迁移）。
- **测试数据库**：`.env` 设 `DATABASE_URL=sqlite:///./test.db` 或 `sqlite:///:memory:`，测试前 `Base.metadata.create_all`（测试不必跑完整迁移链），对标旧 `api.test.ts` 的 `:memory:` 做法。

## 9. 测试方案（P0-1 范围）

1. **模型层测试**：`create_all` 后验证外键/唯一约束生效（如重复 email 报错、CASCADE 删除生效）。
2. **关系测试**：删题 → 选项/卡级联删；删用户 → 练习册/题/记录级联删。
3. **映射测试**：旧数据清洗脚本跑通后断言无脏数据（无 summary==answer、无空 content）。
4. **确定性逻辑测试**：SM-2、章节排序（沿用现有 78 用例的思路，但改为**引用真实源码**而非复制代码）。

## 10. 最终架构决策（已定稿）

| # | 决策点 | 最终结论 |
|---|---|---|
| 1 | 内置题库归属 | 预留系统账号 `id=0` + 系统工作簿 `id=0`（`name='内置题库'`），内置题 `source='builtin'` 归属其下；用户学习记录仍按 `question_id + user_id` 私有关联，实现"题共享、记录私有" |
| 2 | Question 删除策略 | **软删除为主**（`deleted_at`）+ **RESTRICT 保护**（answer_record / wrong_record 不可随删题 CASCADE）；review_card 与 option 仍 CASCADE |
| 3 | 答案唯一来源 | `Question.answer` 是唯一正确答案事实源，`QuestionOption` 只存内容不加 `is_correct`；判题统一基于 `type + answer` |
| 4 | Knowledge 关联 | P0 保持 `Question → Knowledge = N:1`（`knowledge_id` 可空）；未来需要时再加中间表升级为 N:N，现在不过度设计 |
| 5 | summary | 保留 `summary`，仅作辅助学习摘要，**不参与判题与核心业务逻辑** |
| 6 | 主键 | SQLite + 单机为主的架构下，统一 **INTEGER 自增主键**；不为离线同步提前引入 UUID 复杂度 |

**附带确认的补充决策**：
- 日期统一使用本地日期，修复旧系统 `toISOString()` 的 UTC 偏移 bug。
- SM-2 的 `ease` 加上限（如 4.0），修复"连续 easy 无限涨"问题。

## 附：开发者必须理解的知识点清单（15 个）

1. **规范化与实体分离**：为什么"题目"与"错题记录"必须分表——数据语义决定归属。
2. **实体关系类型**：1—N / N—N / 自引用（knowledge.parent_id）如何用外键表达。
3. **主键选择**：整数自增 vs UUID 的取舍（简单/排序 vs 分布式/离线生成）。
4. **复合主键**：review_cards 用 `(question_id,user_id)` 表达"一人一题一卡"。
5. **外键删除行为**：CASCADE / SET NULL / RESTRICT 三种语义的适用场景。
6. **单一真相源**：为什么 `answer` 与 `is_correct` 不能双写（数据一致性风险）。
7. **枚举约束**：type/status/source 用 enum 而非自由字符串的意义。
8. **SQLAlchemy 声明式模型**：Model 是 schema 的唯一真相源，替代手写 SQL。
9. **Alembic 版本化迁移**：为什么需要可回滚、可审计的 schema 变更。
10. **Repository/Service/API 分层**：各自职责与依赖方向（不越级）。
11. **索引设计**：什么字段该加索引（外键、高频查询组合）。
12. **状态机建模**：question status / document status 的状态流转。
13. **审计日志 vs 业务数据**：answer_records 只增不改，wrong_records 可编辑。
14. **日期与时区**：本地日期 vs UTC 对"到期判断"的影响。
15. **种子数据 vs 迁移 vs 测试数据**：三者生命周期与隔离方式。
