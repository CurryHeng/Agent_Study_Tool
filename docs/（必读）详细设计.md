## 1. 设计原则

1. 确定性任务用普通程序；非确定性（理解/生成/判断）才走 LLM。
2. Agent 不直接执行 SQL：工具 → Service → Repository → Database。
3. 决策只发生在主 Agent；专家内部为固定 Pipeline。
4. 写操作两阶段确认（propose→confirm）。
5. LLM 输出三层校验后才入库。
6. RAG 为公共能力服务，不设 RAG Agent。

## 2. Agent 消息与状态

### 2.1 主 Agent 请求/响应

```jsonc
// 请求 POST /api/agent/chat
{
  "message": "把这里改简单点",
  "workbook_id": 4,
  "conversation_id": 12,               // 可选：传入则消息持久化并延续该会话上下文
  "context": { "view": "mindmap", "selected_knowledge_id": 342, "current_question_id": null }
}

// 响应
{
  "task_id": "uuid",
  "reply": "我已将「反向传播」节点简化为……",
  "steps": [ { "tool": "get_knowledge_tree", "args": {}, "ok": true } ],
  "proposals": [ /* 写操作提案，见 §3.2 */ ]
}
```

### 2.2 执行状态

- 主 Agent：LangGraph messages 状态（多轮对话）；`max_iterations=8` 熔断。
- 专家 Pipeline：沿用 TaskState 字段（task_id/user_id/workbook_id/generated_data/review_result/errors）。
- 每轮工具调用记入 `steps[]` 与 `agent_tasks` 表（task_id/user_id/intent/status/error）。

## 3. 工具层设计（workflow/tools.py）

### 3.1 分级

| 级别 | 执行方式 | 工具 |
|---|---|---|
| 读 | 直接执行 | search_documents、get_knowledge_tree/detail、get_question(s)、get_stats、get_due、similar_question |
| 导航 | 返回 UI 指令 | navigate(route) |
| 写 | 两阶段确认 | generate_questions、import_knowledge、update/add/delete_knowledge_node、update/delete_question、favorite_question、analyze_wrong_reason、create_plan |

规则：工具是现有 Service 的薄封装（≤30 行）；**参数必须带语义引导**（如 `topic`）。

### 3.2 写操作 proposal 结构

```jsonc
{
  "proposal_id": "uuid",
  "action": "update_knowledge_node",
  "target": { "knowledge_id": 342, "name": "反向传播" },
  "changes": { "before": "...", "after": "..." },
  "impact": "修改 1 个知识点描述"
}
```

`POST /api/agent/confirm {proposal_id, approved}` 才真正执行；测试必须覆盖"propose 不落库、confirm 才落库"。

## 4. 专家内部 Pipeline

### 4.1 知识专家（import_graph 保留）

```text
解析章节 →（无有效章节时 LLM 章节理解）→ 规则引擎预提取
→ 均匀抽样 + LLM 交叉验证 →（必要时全量提取，上限 30 块）→ 三层校验（失败回环 ≤2）→ 入库
```

### 4.2 出题专家（generation_service 保留）

```text
主题 → RAG 检索（top_k=5）→ LLM 生成（system+user prompt）
→ 结构/业务校验（题型匹配、选项≥2、答案在选项中）→ LLM 审题
→ 不通过回环重生成（共 ≤3 次尝试）→ 入库（source=ai, status=approved）
```

题型五种：`single_choice / multiple_choice / true_false / fill_blank / short_answer`；字段：`type, content, options[], answer, analysis, knowledge_id, difficulty`。

### 4.3 教练专家（新建 services/coach_service.py）

```text
统计聚合（确定性）→ 读取错题+作答 → LLM 归因 {reason_type, explanation, suggestion}
→ 条件分支：需补救 → 调出题专家生成针对性练习 → 输出诊断+建议
```

## 5. RAG 设计

切块（chunk_size=500，按章节）→ 本地 ONNX MiniLM embedding → Chroma（按 workbook_id/knowledge_id 隔离元数据）→ top_k 检索。上传文档成功后自动建索引；删文档级联删向量。检索失败降级为仅名称上下文。

## 6. 数据模型（14 表）

```text
users ─1:n─ workbooks ─1:n─ documents / questions / knowledge(树形 parent_id)
questions 1:n question_options（正确答案唯一事实源 = questions.answer；软删 deleted_at）
questions 1:n answer_records / wrong_records（RESTRICT，历史不可丢失）
questions+users ── review_cards（复合主键；FSRS：state/step/stability/difficulty/due）
users 1:n agent_tasks / refresh_tokens / conversations ─1:n─ messages
api_keys（预留）；系统账号/练习册 id=0
```

**对话历史两表**（2026-08-15 新增设计）：

```text
conversations: id, user_id, workbook_id(可空), title(首条消息截取), created_at, updated_at
messages:      id, conversation_id, role(user/assistant), content,
               steps(JSON), proposals(JSON), created_at
```

历史消息直接作为多轮对话上下文来源（/agent/chat 传 conversation_id 时自动加载）。

删除规则：组合关系 CASCADE；knowledge 父节点、question.knowledge_id 用 SET NULL；conversations 删除级联 messages。

## 8. 前端设计要点

- `api/client.ts`：fetch 封装 + JWT + 401 自动刷新 + `estudy:auth-invalid` 事件。
- `AgentChatView`（新增）：消息流 + steps 过程展示 + 通用确认卡片 + navigate 跳转执行。
- 思维导图：markmap 渲染；节点编辑右键菜单与 Agent 工具共用后端接口。
- 刷题：三模式；FSRS due 分钟级标签（"10 分钟后"）。

---

## 9. 错误处理与日志

- LLM 未配 key → 503 友好文案（LLMNotConfiguredError）。
- Agent 节点失败写入 errors，Result Handler 汇总，不静默吞错；任务日志含 status/error。
- 简答题 LLM 判分不可用时降级用户自评（is_correct=None）。

## 10. 测试策略

- 单元测试覆盖确定性逻辑：parser/chunker/grading/FSRS/校验器/权限。
- Agent 测试断言结构不比对文本；图流程测试 Mock tool_calls。
- 三条核心集成链路：资料导入、AI 出题、刷题闭环。
- conftest 全局隔离：假 embedding + 临时 Chroma + 清空 LLM key（测试绝不触网）。
